# 一个声明凭什么存在

这份文档回答一个问题：仓库里某个能力、模块、类型、词汇或引用，**凭什么存在**。

它不是风格指南。三次真实的退役——`market-data` 的 `Bar`、整个 `market-data`、
以及 T 编号的出处——都是同一个形状，而那个形状不会触发任何工具。写在这里是
为了让下一次遇到同类问题时有一条已经走过的路。

---

## 1. 第一性原理

**存在不是一个断言，它是一个待验证的假设。**

仓库里的每一处声明都在说「有东西需要它」。这句话本身不是证据。能支撑它的只有一件事：
**当下有一个消费者，有一个需求，是它满足的。**

不是「将来可能需要」。不是「它在别的地方也这样」。不是「它写得很详细」。

### 让这件事可判定的不对称

| | 成本 |
|---|---|
| **以后再加** | 一次提交。一个能力被退役的代价，是它当时的理由留在 transcript 里。 |
| **现在留着** | 每一条下游的 Card、测试、fixture、agent 都继承这个假设。而错的假设**静默传播**——建立在它上面的东西全部 validate 通过。 |

`market-data` 就是这个：`features.bars.compute` 已经存在，所以 `Bar` 看起来有依据。
但那条依据本身只是一个声明。没有任何 Card、任何测试、任何实现引用过它。

所以：**没有正面证据的声明，默认退役。** 保留需要证据，不需要默认。

### 为什么这些能活很久

**它们不改动任何东西。** 没有 diff，没有失败的测试，没有语法错误。一个错的
contract 是一个完全合法的文件。它可以一直坐在那里，直到有人特意去问。

这也是为什么它必须是一个**主动的探查**，不能指望工具报出来。

---

## 2. 诊断步骤

按成本从低到高排。先跑最便宜的杀手测试。

### 第 1 步 · 追到链的终点

顺着值或调用往前追，追到底。

- `execution.planner.build_transaction` → `UnsignedTransaction` → **零消费者**。
  链终止于空。
- `features.bars.compute` 的每一个字段都能从 `replay.state.checkpoint` 推出，
  唯一的非逐点字段 `realized_volatility` 是 checkpoint 序列的函数。
  链终止于**一个已经能算出来的东西**。

**终点是空，或者终点是能算出来的，这一条声明就没有工作。**

### 第 2 步 · 找承重的消费者，不是声明它的那个

`depends_on` 里逐条列出的 `uses:` **仍然是一个声明，不是一次使用**。

真正的问题是：**哪一个能力的 input / output / payload / 返回类型需要它？**

`robinhood-application` 声明了 `uses: [signer.lock_state, signer.public_address]`，
列得整整齐齐——而它 6 个能力里没有任何一个提到 signer 的类型。

**逐条列出是最危险的状态**，因为它让一个声明看起来像被证过了。

> **这一步在本架构里无法自动化。** 我试过：写一个检查，比较模块自己
> contract 的类型引用和它声明的 `uses:`。结果是 29 条依赖边报 29 条，**误报率
> 约 97%**。
>
> 原因是结构性的：**一个 contract 声明的是模块「对外发布什么」，不是「内部
> 消费什么」**。模块在实现代码里调 `risk.evaluate`，这个调用不出现在它自己
> contract 的能力签名里。而跨模块读实现代码正是本框架禁止的——所以一条合法
> 依赖的证据，恰好落在 agent 无权读取的地方。
>
> 让 agent 各自可开发的那个边界，同时让这类检查不可自动化。这不是缺陷，
> 是同一件事的两面。第 2 步只能靠人读。
>
> 对比第 4 步（标识符查不到）和 `SCHEMA_DANGLING`（引用指向空）：那两条**是**
> 机械的，因为「引用」和「定义」在同一份 YAML 里，边界不影响它们。所以它们
> 做成了 finding，每次 `validate` 自动跑。**能自动的自动，不能自动的写进
> checklist，不要伪装成工具。**

### 第 3 步 · 找出那句辩解

每一条站不住脚的声明都有一句辩解，而且它**通常是唯一的支撑**。

| 案例 | 辩解 |
|---|---|
| signer | 「paper execution or (after T094) the isolated signer」 |
| `Bar` | 「`features.bars.compute` 已经存在」 |
| `pricing` | 「`features.quote.usdg` 已经在做这件事了」 |
| T 编号 | 「这是任务 T032」 |

**如果那句辩解本身只是一个声明，它就是循环的。** 「它在别的地方也这样」和
「那边有一个」是同一句话的两种写法。

### 第 4 步 · 检验那句辩解**能不能被验证，由谁验证**

`T094` 存在吗？我 grep 了：35 个编号，**任务列表 0 个**。所以不能。

这和 `x-encoding` 没有 `x-source`、和把 fixture 当成世界的样子，是同一个检验。
**一句你无法验证的辩解，是穿着引用外衣的断言。**

顺带一个独立检查：`G-S-G-01` 和 `G-SIGNER-01` 指的是同一件事，两套前缀。
改名没传播，或者抄了两个来源——两种都说明这段文字有本仓库之外的上游。

### 第 5 步 · 判定来源，决定去留

**这一步是最关键的分叉，两种来源的去留完全相反，不能混为一谈。**

| 来源 | 判定 | 处理 |
|---|---|---|
| **外来词汇** | 它在**这里是错的** | 退役。不是缺陷，是移植事故。 |
| **未来能力** | 领域对，当下没需求 | 不自动判错：要么写下可验证的辩解，要么退役。**但不能让它挂在一个查不到的门上。** |

**外来词汇**的识别信号：术语属于另一个领域（`OHLCV`、`symbol`、`trading
session` 出现在一个重放 V4 日志的仓库里）；或引用编号来自一个更大的体系
（T020–T113 挂在 12 个 contract、零实现的仓库上，58 个槽位空洞）。

`market-data` 是前者。T 编号是后者，**但同样是外来的**——它们是另一个项目的
计划编号，和 `OHLCV` 一样属于「不属于这里的东西」。

### 第 6 步 · 问「什么能让它成立」，那个东西是真的吗

signer 的辩解是「实盘执行时会用到」。那么**实盘执行存在吗**？

要实盘就要广播。而广播能力是 `rpc.adapter.logs` 第一行明文排除的
（"no signing, no broadcasting"），全仓零个 contract 承诺提交交易。

**所以辩解指向的东西本身也不存在，洞在下一层。** 这解释了为什么
`signer.sign` 不可达：它的输入是「一笔已经签好名的交易」，而没有任何东西生产它。

### 报告的形状

发现这一类问题时，**它是升级触发点，不是可以顺手改掉的东西**。改一个 contract、
动一个模块的增删，属于「不要静默重设计」那一节。

报告要包含三件事：**追到终点的证据**、**那句辩解的原文**、**第 5 步的来源判定**。
少任何一件，下一个人会重新踩一遍。

## 3. 速查

```bash
# 第 1 步：这个类型 / 值有没有消费者
grep -rn "<TypeName>" architecture/
python3 -m framework.architecture.cli consumers <contract>

# 第 2 步：谁声明的 vs 谁真的需要
python3 -m framework.architecture.cli impact <contract>   # 逐条看 uses 是否对得上某个能力

# 第 3-4 步：辩解在哪，能不能验证
grep -rhoE "T[0-9]{3}|ADR-[0-9]+|G-[A-Z-]*[0-9]+" architecture/ | sort -u
ls docs/            # 有没有承载这些编号的东西？没有 = 不可验证
```

## 4. 同一个检验的其它用法

这套步骤不只用于「该不该退役一个能力」。任何「引用了但查不到」的地方都是同一形状：

- `x-encoding` 没有 `x-source` → 定点编码是个猜测穿了引用的衣服。
- Card 引用 `ADR-016` → 仓库里没有 ADR-016。
- 测试断言一个地址「是正确的」→ 那不是 fixture，是伪装成 fixture 的断言。

共同点是：**引用看起来像支撑，而引用本身是需要被验证的东西。**
